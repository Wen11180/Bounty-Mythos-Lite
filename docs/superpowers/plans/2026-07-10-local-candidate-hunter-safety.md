## Phase 1: Local Network and Desktop Boundary

1. Add launcher tests that reject remote Studio and API base URL overrides.
2. Add desktop shell tests for a sandboxed renderer and generated loopback
   service URLs.
3. Update `apps/studio/launcher.cjs` and `apps/studio/main.cjs` so the
   generated configuration is the only accepted service origin.
4. Change `infra/docker-compose.yml` so Postgres and Redis have no host ports
   and API/Web host bindings are `127.0.0.1`.
5. Add a Compose configuration assertion and narrow FastAPI CORS to the
   configured local Web origin.

Verification:

```powershell
cd apps/studio
npm test
docker compose -f ..\..\infra\docker-compose.yml config
```

## Phase 2: Controlled Workspace Paths

1. Write `studio_workspace` tests for an external root, traversal, external
   artifact, tampered manifest, and symlink escape.
2. Add one canonical workspace-root resolver and one allowed artifact-kind
   resolver. Use them for create, load, import, run, export, and benchmark
   paths.
3. Make Studio routes turn a rejected workspace/path into the same explicit
   authorization response before a file is read.
4. Make the HTTP source-audit route accept only the configured workspace root.

Verification:

```powershell
.\.venv\Scripts\python.exe -m pytest apps/api/tests/test_studio_workspace.py apps/api/tests/test_studio_api.py apps/api/tests/test_source_audit.py -q
```

## Phase 3: Parsed Policy Fail-Closed Scope Guard

1. Add policy parser tests for ambiguous policy, explicit scope, forbidden
   automation, and explicit validation mode wording.
2. Add Scope Guard tests proving `none` and `needs_review` automation deny an
   otherwise approved request.
3. Persist the server-derived rule in the campaign payload and derive campaign
   scope state from it. Do not reuse `allowed_tools` as a validation allowlist.
4. Make Studio launch and validation preflight load the persisted rule rather
   than trusting a request rule or request scope state.

Verification:

```powershell

```

## Phase 4: Secret Persistence, Ownership, and Migrations

1. Add persistence tests for HAR/Postman `name`/`value` and `key`/`value`
   pairs, including campaign and worker task payloads.
2. Extend the central JSON redactor with structured secret-pair handling.
3. Add same-program de-duplication and cross-program isolation tests.
4. Replace global artifact hash uniqueness with a program-scoped constraint in
   a new Alembic migration and update repository lookup accordingly.
5. Add an old-schema migration test and run Alembic before persistent Studio
   and CLI database access.

## Phase 5: Fixed A+B End-to-End Benchmark

1. Add a static, secret-free FastAPI fixture pack with policy, scope, OpenAPI,
   HAR, source code, and independent expectations.
2. Drive the real Studio API intake and research flow from that fixture.
3. Require the expected export-authorization candidate, complete provenance,
   and hard false execution, validation, and report-submission flags.
4. Prove the benchmark does not use expectations generated by the evaluated
   candidate output.
